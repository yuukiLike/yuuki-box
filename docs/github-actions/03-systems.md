# 3 · 跨系统自动化

单仓库构建稳定后，Actions 还能接收外部事件、调用云服务、安排自有机器，并协调 AI 任务。本页先看系统分工，再按需展开实现条件；方案未进行运行验证。

## 一个完整例子：资料更新后重新发布

```text
内容系统发布新版本
  → 可信服务验证事件并触发 Actions
  → 拉取指定版本的资料
  → 生成文档与差异报告
  → 审核本次产物
  → 发布到托管平台
  → 保存版本与处理结果
```

这里有四方职责：内容系统提供版本；Actions 安排执行；脚本转换和检查资料；托管平台保存并对外提供网站。工作流将它们连接起来，不会自动赋予访问权限或长期保存所有状态。

## 外部事件与跨仓库协作

- **`repository_dispatch`**：外部系统通过已授权的 GitHub API 请求发出自定义事件，可附带任务标识和资料版本；工作流需在默认分支存在。
- **`workflow_dispatch` API**：调用一个指定工作流并传入受控输入，适合内部操作面板或发布工具。
- **跨仓库调用**：中央仓库通过 API 安排多个仓库的任务，再收集结果；或让多个仓库调用同一份 reusable workflow。
- **`workflow_run`**：一个工作流完成后启动另一个，适合解耦阶段；必须核对前序运行的结果、来源和产物，不能把“完成”直接当成“可信且成功”。

`GITHUB_TOKEN` 通常限定在当前仓库。跨仓库访问需配置权限范围合适的 GitHub App 安装 token 或其他受限凭据，不能假设当前 token 能管理整个组织。

外部事件可能重复到达。发布版本、发送消息或创建记录时，应保存业务任务 ID 与已处理状态，重复请求返回已有结果。单纯设置 `concurrency` 不能代替长期去重。

GitHub 对使用仓库 `GITHUB_TOKEN` 产生的事件有防递归规则：这类操作通常不会再触发新的工作流，`workflow_dispatch` 和 `repository_dispatch` 等有明确例外。若计划“机器人提交 → 自动再构建”，需先核对这条链是否受限。

应按实际任务设计入口，而不是随意换成更大权限的凭据。需要跨仓库或事件接续时，用范围明确的 GitHub App，并让程序防止循环调用和重复交付。

## 云端身份与部署权限

传统做法是在 GitHub Secrets 中保存云平台密钥。支持 OIDC 的平台可改为：

1. 工作流请求 GitHub 签发的短期身份令牌。
2. 云平台核对组织、仓库、分支或 environment 等身份条件。
3. 只给符合条件的运行一份短期云凭据。
4. 部署脚本在这份凭据允许的范围内操作。

`id-token: write` 允许请求身份令牌，不等于已经获得云管理员权限。真正能做什么由云平台信任策略与角色权限决定；只允许预期仓库和发布环境取得所需权限。

对不支持 OIDC 的 API，仍可使用 Secrets 保存密钥，但需要限制可读取它的任务，并考虑轮换与过期。日志掩码不能保证所有变形后的秘密都会被隐藏。

## 哪些场景适合自托管 runner

- **专用硬件**：自有 Mac、GPU、特殊 CPU 架构，或需要连接实际设备。
- **内网资源**：内部镜像、数据库、构建集群等无法由普通公网 runner 直接访问的系统。
- **定制环境**：较大的编译缓存、专用 SDK、许可证软件，或需要控制机器生命周期。

自托管意味着机器、电费、补丁、磁盘清理、并发和故障恢复由使用方负责。重型任务也可以由 Actions 只提交到外部计算集群，再由其他服务记录状态；无需让一个 job 一直等着。

在自有 Mac 上构建示例是可选方向，但机器必须在线并满足工具与签名条件。不要让公开 PR 的任意代码直接进入存有个人数据、发布密钥或内网权限的长期 runner。

涉及不可信候选代码时，需要可销毁、隔离的执行环境；容器、独立目录或两个 job 的名字本身都不能证明隔离已经成立。

## AI 可以加入哪些步骤

从只读到写入，复杂度逐级增加：

1. **摘要与分类**：把构建日志、提交记录或待处理事项整理成报告，供维护者判断。
2. **候选内容**：生成更新日志、翻译草稿、文档修改建议，记录模型与输入来源。
3. **候选代码**：在已批准范围内修改代码，交给独立环境检查，再产出草稿 PR。
4. **多 Agent 协调**：把编码、审查、验收拆给不同执行者，由程序维护任务状态、版本与交付条件。

Actions 负责安排步骤，模型 API 或 Agent 服务负责推理与工具执行。ChatGPT、Copilot 或其他产品的订阅，不应被默认视为任意模型 API 的额度；相关服务单独核对计费。

<mark class="key">问题是否成立、适不适合自动处理、是否获准执行，需要分别判断</mark>。标签只是筛选条件；批准需对应批准者、任务内容与代码基线。Issue、评论、模型输出和候选代码均作为外部输入处理。

## 权限在哪一步容易越界

- **PR 事件**：普通 fork PR 通常没有仓库 Secrets 或写 token；不要用 `pull_request_target` 取得高权限后执行 PR 分支中的脚本。
- **表达式进入 shell**：Issue 标题、评论和分支名等内容不要直接插进命令源码。通过环境变量传值、正确引用，并限制业务允许的输入。
- **分离验证与发布**：候选代码不能共享后续可信检查的可写环境；验证与发布必须使用同一份固定产物，并核对验收条件和测试改动。
- **第三方 Action 与外部 API**：明确传出了什么资料、授予了什么权限，以及失败或重复请求后会留下什么结果。

这些是设计要求。本专题没有完成不可信代码隔离、凭据、网络或发布链路验证，不能据此认定已经具备无人值守交付能力。

## 什么时候应该把工作移到其他平台

- **常驻服务、WebSocket 或交互桌面**：使用应用服务器或专门的桌面环境，Actions 只负责构建和部署。
- **精确定时或必须处理每个事件**：使用可靠队列、调度器与数据库，保存重试、超时和去重状态。
- **超长计算、大模型训练或高频推理**：使用合适的计算平台；Actions 可以提交任务和整理结果，但仍受 job 时限、资源与平台条款限制。

最后用[额度与费用](04-costs.md)估算运行频率、矩阵规模、产物保留期与外部服务成本，再决定自动化范围。
