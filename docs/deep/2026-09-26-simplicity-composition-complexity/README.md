# Deep 调查：简单、组合、复杂性

调查日期：**2026-09-26**。这轮基于既有 docs，继续研究 Raycast、Warp、Zed、Grok Build，并以 PI-Desktop 和 Yuuki Box 的实际代码作对照。主题从“用了什么技术”推进到三个问题：**什么变简单了，什么可以组合，剩下的复杂性由谁承担。**

**核心判断：这些造物值得学习的地方，是让少数稳定的操作单位承载丰富能力，并持续维护这些单位之间的契约。** 接口统一只是起点；状态归属、时间顺序、取消、副作用和资源寿命决定组合能否可靠工作。这个判断来自以下案例分析，不是各产品共同发表的设计宣言。

## 比上一轮多挖到什么

1. **组合有层次。** 呈现组合、能力复用、可靠任务衔接和跨进程部署，分别需要不同保证。Warp 的共同滚动区域不能证明所有执行对象同构；Raycast 的 `launchCommand` 启动确认不能当作完成结果。
2. **抽象有失效点。** Zed 的内部 Agent crate 仍绑定应用体系；Grok 可复用定义与 Builder，但构建后的 Agent 有会话上下文；同名接口和独立目录都不能证明可随意抽走。
3. **复杂性可以减少。** 去掉重复权威、缩小并发范围、延后不需要的通用性，会减少实际状态与同步关系；把部署或桥接交给平台，则主要改变承担者。两种情况应分开写。
4. **极简要保留关键事实。** Whisper 的转写阶段、工具写入后再取消的副作用、流的终态，都影响下一步行动，不能为减少界面状态而抹掉。
5. **本地项目在变化。** 本轮期间共享 Swift Agent runtime、工具循环、持久会话与 Whisper 扩展已经出现实现，文档入口也同步更新。它们还没有真实 API/录音与端到端验收，不能继续用“只有 UI 样例”概括，也不能写成运行验证完成。

第 1 项详见 02/01，第 2 项详见 03，第 3 项是 01 的研究归纳，第 4/5 项详见 04。这里没有新增技术栈决策、改写应用代码或要求先建设完整平台。
