# 云端电脑实测：CPU、内存、Shell 与多对话

**2026-11-01，我开始在 Codex Cloud 里操作 `yuuki-box`，让 Agent 执行命令、查看机器资源和 Git 记录。** 本次环境测得 **4 vCPU 配额、32 GiB 内存上限、约 63 GiB 工作区磁盘**。下面记录如何读懂这些数值，以及开两个对话时应该怎样判断资源占用。

这些是本次实例的观测值，不能当成所有账号、套餐或后续任务的固定规格。这里说的「云端电脑」指任务的托管执行环境；容器内看到的资源，也不能直接当作独占物理服务器的配置。

## 先看这次实际测到了什么

| 项目 | 本次观测 | 怎样理解 |
| --- | --- | --- |
| 系统 | Debian GNU/Linux 13.6，x86_64 | 可以运行 Linux 开发工具 |
| CPU | 可见 5 个逻辑 CPU；配额为 4 vCPU | 并行工作要参考配额，不能只数可见核心 |
| 内存 | 上限 32 GiB | 来自 cgroup 限制，不是当前已用内存 |
| 工作区磁盘 | 总容量约 63 GiB，当时可用约 59.7 GiB | 来自 `/workspace` 所在文件系统；安装依赖后可用量会变化 |
| Swap | 未发现已启用的交换空间 | 内存紧张时不能假定还有磁盘交换空间可用 |
| 工作目录 | `/workspace` | 本次仓库位于 `/workspace/yuuki-box` |
| 执行状态 | `running / connected`；`pwd` 成功 | 状态查询与实际命令都已确认连通 |

资源够不够，要结合任务判断。阅读文档、修改代码和构建网站可以先按仓库命令验证；这张表没有测量构建速度，也没有验证 GPU 或大模型推理能力。

<details class="qa">
<summary>为什么看见 5 个 CPU，却说只有 4 vCPU 配额？</summary>

本次 `/sys/fs/cgroup/cpu.max` 返回：

```text
400000 100000
```

两个数分别是配额和周期，单位均为微秒。`400000 ÷ 100000 = 4`，表示每个周期最多使用相当于 4 个 CPU 的时间。进程可以在可见 CPU 上被调度，但持续 CPU 用量仍受配额约束。读到 `max` 则表示这一层没有设置配额，仍需检查其他限制。

内存文件 `memory.max` 返回 `34359738368` 字节，即 `34359738368 ÷ 1024³ = 32 GiB`。`free` 或 `/proc/meminfo` 中的总内存可能属于更大的运行环境，判断本任务限制时应结合 cgroup。

</details>

## 在自己的对话里复查

可以直接把这个任务发给 Agent：

```text
只读检查当前云环境的系统、架构、CPU 配额、内存上限和工作区磁盘。
区分可见 CPU 数与实际配额，区分内存上限与当前用量。
列出实际读取的文件或命令；无法读取的项目明确标为未知。
再执行 pwd，定位项目后报告 Git 分支和最近 5 条提交。
本轮不修改文件、不安装软件、不推送。
```

本次使用的是 Linux cgroup v2，可以让 Agent 执行以下命令：

```bash
# 系统与架构
cat /etc/os-release
uname -m

# 可见 CPU 与资源限制
python3 -c 'import os; print(os.cpu_count())'
cat /sys/fs/cgroup/cpu.max
cat /sys/fs/cgroup/memory.max

# 磁盘与交换空间
df -h /workspace
swapon --show

# 项目状态
git -C /workspace/yuuki-box status --short --branch
git -C /workspace/yuuki-box log -5 --oneline
```

仓库路径按实际位置替换。`df -h` 会四舍五入显示容量；本页的 GiB 按 `1024³` 字节换算。其他环境的 cgroup 路径可能不同，文件缺失不能解释为「资源无限」。

## Shell：通过 Agent 执行，还是自己 SSH？

**本次已经验证的是 Agent 执行 Shell。** 在对话里说「查询当前项目的 `git log`」，Agent 就能在云端执行并返回结果。也可以给出具体命令，让它查看文件、运行测试或启动开发服务。

自己从电脑终端通过 SSH 登录，需要平台另行提供连接入口、地址和认证方式。本次没有取得这样的入口，也没有验证直接 SSH。若你使用的产品界面提供 Terminal，可按该入口操作；不能仅因 Agent 能执行 Bash，就推断用户一定有交互终端或 SSH 权限。

## 两个对话，会一直占着两台机器吗？

**两个独立云任务有各自的工作状态；两个聊天窗口并不足以说明有几个运行实例。** 新任务可以复用同一个已发布环境，但配置和文件快照的复用，不表示共享正在运行的服务进程。[官方环境与状态说明](https://learn.chatgpt.com/docs/environments/cloud-environments#reuse-and-update-saved-state)

| 场景 | 可以据此判断什么 |
| --- | --- |
| 两个窗口打开同一任务 | 窗口数量不能用来计算实例数量 |
| 两个独立任务选择同一个已发布环境 | 可以有相同起点；任务中的文件修改不会因此自动同步 |
| 两个不同实例都处于运行状态 | 可能同时占用两份计算资源；不等于两台独占物理服务器 |
| 对话保留着，或者窗口被关闭 | 不能单凭这一点确定实例仍在运行、已经挂起或已回收 |

需要确认是否共用时，让两个对话分别读取当前环境的 `environment_id`。相同表示同一个环境实例，不同表示不同实例；再分别检查运行状态。如果工具没有提供实例标识，就保留为未知。本次只检查了当前实例，**没有同时启动第二个任务来测量并发资源占用**。

<details class="qa">
<summary>空闲挂起、状态保留和计费，是一回事吗？</summary>

运行中的计算资源、可恢复的文件状态、聊天历史，以及套餐用量分别描述不同事情。环境状态可以保留，不代表 CPU 一直在执行任务；关掉窗口也不能当作资源已释放的证据。

本次没有测量空闲挂起和回收时间，也没有验证按实例计费的规则。需要结合[环境生命周期说明](https://learn.chatgpt.com/docs/environments/cloud-environments)和[套餐用量说明](https://learn.chatgpt.com/docs/pricing)判断，不能把「打开两个对话」换算为「持续支付两台服务器的费用」。

</details>

## 这次遇到的初始化握手超时

准备环境时曾出现 `exec-server initialize handshake` 等待 10 秒超时，随后执行命令返回没有可用的执行环境。后来环境实例发生变化，状态显示 `running / connected`，并成功执行了 `pwd` 与 `git log`。这些现象确认了后续实例能够执行命令，尚不能确定最初超时的根因。

遇到类似情况，先让 Agent 检查当前实例状态，再执行一个最小只读命令。只看到 `running` 还不够：本次一度出现状态已运行、命令通道仍不可用的情况。命令恢复后，再继续安装、构建或测试；连通成功本身不能证明项目依赖已经就绪。

完成一次资源查询和项目状态检查，就可以回到实际开发任务。需要重新准备环境时，接着看[创建并发布环境](01-for-safe.md#-创建并发布环境)；想安排自动交付，再看 [Issue 到 PR 的并行实验](05-issue-to-pr.md)。
